Experiment notebook · jev-lint · updated 26 Sep 2026

Jev as a fuzzy linter for coding agents

Can a small, fast judgment model check an agent's code after every edit, against rules no deterministic linter can express, and does the agent get better for it? This notebook logs each experiment, newest first. Older results stay here; when a newer run replaces a number, the old one is marked superseded.

    Entry 4 · Local models on the Mac 26 Sep 2026 latest

    Question. Can a Jev-like model running on this machine (M3 Max, 64 GB) replace the API call? The goal is zero cost per edit and lower latency, ideally using the Apple Neural Engine.

    Setup. Three open models all speak the same /v1/systemone protocol, so the hook and harness only needed a base-URL switch (TYPESAFE_BASE_URL):

    • Kev-0.8B and Kev-4B, fine-tuned Qwen models running on MLX (the GPU, bf16);
    • Laya, a 421M-parameter ModernBERT encoder, on PyTorch's Metal backend.

    The rules and held-out edits are the same as in Entries 1 and 3, with the same 0.8 / 0.5 thresholds. Requests ran one at a time so the timings aren't shared. No model was fine-tuned: this is zero-shot.

    Accuracy

    {{CHART_LOCAL_F1}}

    "Best threshold" is Kev-4B's F1 at whichever cut-off suits it best, which was 0.6 in every group. It's picked on the held-out data, so it flatters Kev-4B.

    Full table for all three local models{{LOCAL_TABLE}}
    • Kev-4B is the only usable one, and it's well behind. Its F1 is 54–67% with both tiers, and 61–74% at its best threshold, against Jev's 96–99%. Its high tier is precise ({{KEV4_HIGH}} findings real) but catches only 14–31% of violations. Its double-check tier flags 25–74% of clean edits.
    • Kev-0.8B and Laya are close to chance on code. Their F1 is 13–34%, and they flag most or all clean edits. On a two-rule probe, Kev-0.8B even scored the clean file higher on "empty catch" than the file that had one.
    • Laya's context limit is a structural problem. The English checkpoint reads 512 tokens, and larger edits are cut off.

    Speed

    {{CHART_LOCAL_LAT}}

    Every local model was slower than calling Jev's API. Kev-4B's 90th percentile reached 8–10 s on long Swift and practice-rule edits, and one request timed out. Running locally removes the per-call cost (about $1.51 per 10,000 edits with Jev), but it adds seconds to every agent edit.

    The Neural Engine

    Kev runs on MLX, which uses the GPU, not the Neural Engine. Laya is the natural candidate for it: an encoder with no text generation. We exported its encoder to ONNX and ran it through ONNX Runtime's Core ML provider. The export matched PyTorch to within 1e-4.

    {{BENCH_TABLE}}

    One lint request is 21 rules × 512 tokens. "Core ML coverage" is how much of the graph Core ML accepted; the rest ran on the CPU.

    • Core ML accepted only 144 of 1,677 graph nodes. ModernBERT's attention and masking ops fell back to the CPU in 29 separate pieces, so every compute-unit setting ran at CPU speed (15–22 s).
    • Converting the PyTorch model straight to Core ML with coremltools failed on unsupported ops (new_ones, then boolean mask arithmetic). Patching those is a project of its own.
    • Even a perfect port wouldn't beat Jev. Laya encodes the code once per rule, about 10,000 tokens for 21 rules. That's roughly 8.6 trillion operations, which takes at least half a second at the M3 Max Neural Engine's quoted 18 TOPS, and more in practice. Jev and Kev encode the code once for all rules.

    Can it be faster?

    We profiled Kev-4B on real held-out edits: a 6-line edit and a 138-line edit, a new edit versus the same edit sent again. Kev already runs on the GPU (Metal, through MLX). Cold start from launching the server to the first answer was 22.8 s, so it has to stay resident. All numbers below are warm.

    13 (hygiene)3.98 s3.44 s3.59 s2.02 s
    23 (both packs)8.49 s7.90 s5.95 s5.10 s
    • The number of rules dominates. Each rule is a separate "row" that re-reads the cached code. On Metal, Kev runs those rows one at a time: its source says so, to keep memory bounded. That costs roughly 250–350 ms per rule even on a 6-line edit.
    • The code itself is cheap once cached. Re-sending the same 138-line edit with one rule dropped from 2.5 s to 0.29 s, thanks to Kev's prefix cache. Shortening the rule text by half (dropping the criteria) cut the 6-line case only to 6.1 s. It's the row count, not the words.
    • Levers, in order of payoff:
      1. Ask only rules that apply to the file. A cheap keyword gate (React rules only when hooks or JSX appear, SwiftUI rules only with import SwiftUI) would often cut 23 rows to 5–8. That helps Jev's cost too, but needs its own recall check.
      2. A smaller fine-tuned model. The 0.8B model's rows are several times cheaper, if fine-tuning brings its accuracy up.
      3. Batch rows on Metal. That's a change inside Kev's MLX path.
      4. An async hook, so the agent isn't waiting at all.
    • A faster GPU mostly means a different machine. Kev batches rows with CUDA graphs on NVIDIA, but a server on the DGX Spark adds a network hop and isn't "local" in the zero-cost-on-this-Mac sense.

    Estimate: with gating plus a fine-tuned small model, 0.5–1.5 s per edit on this Mac looks plausible. Beating Jev's ~0.3 s locally is unlikely without batched rows.

    What we learned

    1. Zero-shot local models can't judge these rules yet. Kev-4B is the closest, at about 70% F1, and it's 7–14× slower than Jev's API on this Mac.
    2. The Neural Engine isn't reachable with today's exports, and Laya's one-pass-per-rule design would cap its speed anyway.
    3. The promising path is fine-tuning, not a bigger download.
      • Kev ships a fine-tuning recipe, reported at about $1 per Kev-4B run.
      • Our labeled edits (roughly 9,000 rule judgments) are a ready training set.
      • Rules and cases can be generated further by the jev-lint-rules skill.
      • Training on Jev's own outputs would need a check of TypeSafe's terms first.
    4. Latency can be hidden instead of beaten. Claude Code hooks can run in the background and wake the agent only when a finding comes back (asyncRewake). A slower local model might then be fine, but this is untested.

    Before the AI reviewer

    Setup. Claude Code (Sonnet) built 12 new features, 6 React and 6 SwiftUI, with no hook, twice each. Examples: debounced search, a polling dashboard, a WebSocket chat, a stopwatch, and async wrappers around a callback SDK. An AI reviewer (GPT-6-Luna) then reviewed the final code with no knowledge of our rules. A second pass matched each review finding to a rule, or to "none". We replayed Jev over every edit the agent made, to see what the hook would have said before the review.

    {{CHART_FUNNEL}}

    In the practices round the reviewer raised {{FP_FINDINGS}} issues. {{FP_IN}} ({{FP_IN_PCT}}) matched one of our rules, and Jev had flagged {{FP_CAUGHT}} of those ({{FP_CAUGHT_PCT}}) during the edits: {{FP_C8}} at "fix" and {{FP_C5}} at "double-check". It reliably caught the literal patterns, such as await res.json() cast to a type without validation.

    The {{FP_MISS}} misses are subtler relatives of a rule:

    • overlapping polling loops or debounce races outside a useEffect fetch, scored 0.04–0.10;
    • a concurrent-upload bug that could strand a continuation, scored about 0.3.
    The round-1 tasks (retry helpers, rate limiters, caches) show the same limit more starkly. Only {{R1_IN}} of {{R1_FINDINGS}} reviewer findings touched any rule; the rest were logic bugs.

    Jev also flagged issues the reviewer never mentioned, mostly hygiene items like empty catches, force-unwraps and vague names. A separate rule grader confirmed most of them as real.

    Hook on vs off

    Same 12 tasks, same repeats, with the hook on (both packs, both tiers).

    {{CHART_HOOK_REVIEW}} {{CHART_HOOK_OUT}} {{HOOK_TABLE}}
    • Rule violations fell, and this time the drop is significant. The paired change in graded violations per task was {{PD_ALL}}. Practice-rule violations alone changed by {{PD_P}}; most of that was unvalidated JSON (10 → 2).
    • The review improvement came from the React tasks. There, rule-covered review findings fell from 1.42 to 0.25 per task. On the SwiftUI tasks, the reviewer raised few rule-covered issues either way, and slightly more with the hook (0.42 → 0.67 per task, that is 5 → 8 findings). That's too few to read anything into, but it isn't an improvement.
    • The reviewer's other findings didn't change overall. Findings no rule covers stayed at about 3 per task. They moved in opposite directions on React (2.83 → 3.50) and SwiftUI (3.25 → 2.50), which looks like noise. The hook fixes what it checks, and nothing else.
    • Cost. Every run built. There were {{HOOK_CALLS}} hook calls with {{HOOK_ERRS}} errors, at about 0.32 s each. Agent cost rose 26% and time rose 14 s per task, from the fix-up edits.

    What we learned

    1. Wording is the whole game. Jev answers the words, not the intent. Rules need the exact pattern plus explicit exceptions ("WebSockets are not HTTP requests"). One tuning pass, checked on unseen edits, removed most false alarms.
    2. Jev catches patterns, not reasoning. It finds "cast JSON without validating" every time, but not "two polling loops can race".
    3. A hint beats a review comment, where the rules match the work. The agent fixed hook findings in its next edit. On React tasks, the reviewer had far fewer rule-covered issues to raise. The Swift practice rules rarely matched what the reviewer cared about (5 of 44 findings), so there was little to prevent.
    4. Luna is a strong alternative judge. It's slightly more accurate on these rules, but about 5× slower per edit, and it doesn't return probabilities for tiering. Jev's speed matters because the hook runs on every edit.

    Entry 1 · Hygiene pack 26 Sep 2026

    Question. Following the forwarded post: convert coding guidelines into tiny rules that are easy to judge, and run Jev on every edit in a PostToolUse hook. Findings come back in two tiers. Does it work in TypeScript and Swift?

    What we built. src/hook.ts works in Claude Code and Codex. It extracts only the code the edit added, including the + lines of a Codex patch. It asks one yes/no question per rule in a single Jev call, and returns findings as extra context. It never blocks, and if Jev is slow or down it stays silent. There are 13 rules per language, such as no any, no empty catch, no restating comments, and no magic numbers.

    Labeled edits

    {{N_H_ALL}} synthetic hook payloads, split into tuning and held-out sets. The original comparison used GPT-5.4-mini as the LLM judge (see Entry 2 for both baselines side by side).

    • Jev: 99% held-out F1 in both languages at p ≥ 0.5, and no false alarms on clean edits.
    • GPT-5.4-mini: 90–94% F1, and it flagged 8–21% of clean edits superseded baseline.
    • Regex: 61–66% F1 overall, because it can express only half the rules.
    • Run-to-run stability: Jev's probabilities moved by at most {{CONS_MAX}} across repeats (99th percentile {{CONS_P99}}).
    • Weak spots: rules that need counting (nesting depth: 70% recall) or tracing (floating promises: 75%).

    Real agent runs

    Claude Code (Sonnet) did 12 general tasks, such as a GitHub client, a rate limiter and a disk cache. Each ran twice under three conditions: no hook, both tiers, and high tier only. GPT-5.5 graded the final files blind.

    • The agent acted on the feedback. It fixed 19 of 20 high-tier findings, and mechanical violations went to near zero. For example, Swift force-unwraps fell from 6 to 1.
    • The overall effect was small. Violations per task went from 2.29 to 1.83 with both tiers, and to 1.71 with the high tier only. The 95% interval includes zero.
    • Why. The agent already wrote fairly clean code, and most of what remained were judgment calls on names and numbers.

    These numbers used the hygiene pack only. The full v1 page is kept at report/archive/2026-09-26-v1-hygiene-report.html.

    Jev vs the grader on real code

    On 98 real agent-written files, Jev and GPT-5.5 agreed on mechanical rules. They split on vague names and magic numbers. Mostly that was the grader reading the rule literally: let (data, _) = … fails because data is on the banned list, and defaulted option values count as magic numbers. Jev's one clear miss was four-level nesting.

    Recommendation

    1. Install the hook with both packs in Claude Code (and Codex once its CLI is fixed on this machine). Run it as a non-blocking hint with thresholds 0.8 / 0.5, and pin JEV_LINT_MODEL=jev-1.13.0.
    2. Let each repo learn from the hook. The findings log records what fired and whether the agent fixed or kept it. Run the jev-lint-learn skill weekly on active repos: it turns recurring fixes into AGENTS.md guidance, and repeatedly ignored flags into rule rewrites. In its first real use, it narrowed this repo's own stdout rule after a false positive.
    3. Keep the AI code reviewer. The hook handles the pattern-level issues cheaply before review, so review time goes to logic and design, which is where about 75% of review findings were.
    4. Treat rule wording like code. Before adding a rule, add labeled examples and hard negatives, tune on the dev split, and accept it only if the held-out split holds up. The harness does this in one command.
    5. Consider the high tier only for practice rules if noise shows up in practice. Their double-check band was 64% real, compared with 86% for hygiene rules.
    6. Move nesting depth and floating promises to ESLint/SwiftLint. Jev is weak at counting and tracing.

    Next experiments

    • Fine-tune Kev-4B (then Kev-0.8B) on our labeled edits, and re-run Entry 4. The bar to beat is Jev's 96% held-out F1 at about 0.3 s. Check TypeSafe's terms before training on Jev outputs.
    • Try an async hook (asyncRewake) so a slower local judge doesn't block the agent, and measure whether late feedback still gets acted on.
    • Neural Engine, only with a model built for it. A shared-state encoder in Apple's Neural Engine layout, if a fine-tuned small model turns out accurate enough.
    • More coverage of the reviewer's categories. Try rules for the misses (debounce and poll races, continuation cancellation), and check whether they stay precise.
    • Bigger end-to-end runs. More repeats, a weaker and a stronger agent model, and real repositories instead of scaffolds.
    • Codex end to end. Blocked for now: the Codex CLI's platform binary is missing on this machine.

    Methods

    • Jev: jev-latest (jev-1.13.0), one call per edit, one yes/no question (a Noul) per rule. $0.042 per million input tokens; output tokens are free.
    • LLM judge, grader, reviewer and mapper: GPT-6-Luna at reasoning_effort: low. $0.10 per million input tokens and $0.50 per million output, standard tier, checked 26 Sep 2026. Entry 1 originally used GPT-5.4-mini and GPT-5.5.
    • Local models (Entry 4): Kev-0.8B and Kev-4B (jaredpalmer/kev-*, MLX, bf16); Laya 0.3.20 English checkpoint (PyTorch Metal backend; ONNX Runtime 1.30 with the Core ML provider). Held-out split only, one request at a time, on an M3 Max with 64 GB.
    • Agent: Claude Code headless (Sonnet). User hooks, plugins and MCP servers were off. Hook conditions were interleaved.
    • Labels: written by Claude subagents, one labeler per edit. Tuning and held-out sets come from different authors. Thresholds were fixed at 0.8 / 0.5 before any data came in.
    • Caveats:
      • The labels are synthetic.
      • Luna is both the competitor and the grader, so shared blind spots could favour it.
      • The end-to-end samples are small: 24 runs per condition.
