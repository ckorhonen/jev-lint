Experiment notebook · jev-lint · updated 26 Sep 2026

Jev as a fuzzy linter for coding agents

Can a small, fast judgment model check an agent's code after every edit, against rules no deterministic linter can express, and does the agent get better for it? This notebook logs each experiment, newest first. Older results stay here; when a newer run replaces a number, the old one is marked superseded.

    Entry 6 · JevLike, and is the hook worth its cost? 26 Sep 2026 latest

    JevLike

    Question. Is JevLike better trained than Kev or Laya for this?

    What it is. It's a training kit rather than a pretrained judge. It provides an option-attention scoring head, which you train on your own labeled data over either a byte encoder learned from scratch or a frozen Hugging Face encoder. Its only released checkpoints are for Doom, chess and synthetic menus, so there's nothing to run zero-shot on code rules.

    So we trained it on our own labels. The training data was the tuning split, 5,536 rule judgments with only 342 violations (about 10 per rule); held-out edits were used only for scoring. The labels are the subagent-written ones, not Jev outputs. Each row was "Rule + exceptions + code → no/yes". We trained two variants, using its recommended settings:

    • a byte encoder from scratch with 4 KB of context;
    • a frozen Qwen2.5-0.5B with a rank-256 head, 768 tokens of context and 4 epochs on the Mac GPU.
    {{JEVLIKE_TABLE}}
    • Neither learned the task. Both validation losses (0.283 and 0.279) sit at the "always guess the base rate" level (0.288). Neither ever reaches p ≥ 0.5, and even the best possible threshold gives 10–47% F1 while flagging most clean edits.
    • It's fast: {{JEVLIKE_MS}} ms per rule for the Qwen variant. Speed was never the problem; the training data is. A frozen encoder plus a small head needs far more than about 10 examples per rule to learn a judgment like "this effect only derives state".
    • For fine-tuning, start from a model already trained to judge text (Kev, whose decision head is pretrained) rather than from a bare encoder, and grow the labeled set. That's the Entry 5 plan, unchanged.

    Is the hook worth its cost if a reviewer would catch it anyway?

    Setup. We took the Entry 5 Claude Code runs and gave each one the AI reviewer's comments (Luna, blind), exactly as a review would send them. The same agent (Sonnet) then did one fix round. Four pipelines:

    • no hook;
    • sync Jev hook;
    • async Jev hook;
    • async Jev hook left on during the fix round too ("always on").

    The graded rule violations are measured on the final code.

    {{CHART_PIPE_COST}} {{CHART_PIPE_VIOL}} {{PIPE_TABLE}}
    • The hook never saved a fix round. All 24 no-hook tasks got review comments (3.6 per task), and only 2 of 24 got nothing but rule-covered comments. A fix round costs about $0.17–0.19 and 70 s whichever pipeline came before it. So the hook's roughly $0.05 is not paid back in cheaper remediation.
    • The review loop narrows the gap, but doesn't close it.
      • Before review, the hook halves violations (2.38 → 1.21 async).
      • Review plus fix takes the no-hook code down to 1.67; always-on ends at 1.08.
      • With 24 pairs, that difference isn't yet significant (95% CI crosses zero).
      • The reviewer only ever flagged about 40% of rule violations, so the rest survive review.
    • Fix rounds create new violations. Without the hook, the fix round raised the violation count in 7–8 of 24 tasks in the hook arms, from new code nobody checked. With the hook left on, it caught 14 issues in 12 of the 24 fix rounds.

    When the cost is justified:

    • Human review. Before review, the hook halves the rule-covered comments a reviewer would otherwise write (sync: 0.96 → 0.50 per task). At about $0.04 per task, it's cheap against even one minute of a reviewer's time.
    • No AI review on every change, for example local iteration, long agent sessions and small commits. There the hook is the only check, and it cut violations by about half with significance (Entry 5).
    • Review latency. A real review cycle (CI, queue, reviewer) takes minutes to hours. The async hook's cost is about 10 s of agent time, and the agent doesn't wait for it.

    When it's marginal: when an AI reviewer and a fix round already run on every task. Then it only buys the residual quality, roughly 35% fewer rule violations (not yet significant), for about +17% agent cost. A cheaper design for that setup: run the Jev check once at review time, in about 0.3 s per file and with no extra agent turns, and add its findings to the reviewer's comments. The single fix round then covers both. That's untested.

    Entry 5 · Rule gate, async hooks, new rules, Codex 26 Sep 2026

    Question. Entry 4 found that the local model's time grows with the number of rules asked, and that hooks block the agent while they run. Four questions follow. Can a cheap pattern gate skip rules that can't apply without losing catches? Does running the check in the background (Claude Code's asyncRewake) still change the agent's code? Does the hook work in Codex? Do the new rules for the reviewer's misses hold up?

    Changes in this entry:

    • Gate: every rule got a when pattern, such as useEffect or Continuation, and is only asked when it matches.
    • Dropped rules: nesting depth and floating promises moved to ESLint (max-depth, no-floating-promises).
    • New rules: three, each with fresh labeled edits from two independent authors:
      • overlapping polling or debounced requests;
      • continuations without cancellation;
      • stored continuations that a second call can overwrite.
    • Rule boundaries: the new rules overlapped with older ones, so their boundaries were written into the rules using the tuning split only.

    Rule gate

    {{CHART_GATE}}

    Across all labeled edits, an edit is now judged against 3.0–5.0 rules instead of 11–13, so two thirds of the model's work disappears. On held-out edits, the gate cost no recall for Jev or Luna. One pattern did cost a catch at first: the overlap rule's pattern knew timers and polling but not fetch. We broadened it to "makes a request"; the gated numbers below are after that fix.

    Held-out F1, recall and false alarms, all rules vs gated{{GATE_TABLE}}

    The gate is a regex prefilter, so it can only remove flags, never add them. Its patterns are deliberately broad ("the code mentions useEffect"). They don't try to detect the violation itself, which stays the model's job.

    Rules for the reviewer's misses

    {{NEW_RULE_TABLE}}
    • The new rules work. On held-out edits, overlap caught 10 of 10, cancellation 12 of 12, and stored-overwrite 9 of 9, with 0–1 false flags each.
    • The older neighbours needed boundaries. swift-continuation-misuse started firing on the new cases (13 false flags on the tuning split). After its exceptions named the new rules, it made 5 false flags on held-out edits. Fetch race still has 4. Both are worth another wording pass, and Swift practice rules are now at 93–94% F1, against 96% before the harder cases arrived.

    Kev-4B with the gate

    {{CHART_KEV_GATE}}

    Gating helped Kev on both fronts. F1 rose to 70–75%, because it stopped answering rules that couldn't apply, and median time fell from {{KEV_LAT_BEFORE}} s to {{KEV_LAT_AFTER}} s per edit. It is still well behind Jev's 94–100%.

    Batching on Metal was already done. Kev's MLX path runs all of a request's rule rows in one batched pass, with up to 57 rules per pass for a short edit. Forcing one rule per pass made it 10–34% slower. The remaining cost is plain compute, about 114 tokens per rule through a 4B model, so fewer rules (the gate) or a smaller model are the levers.

    Claude Code runs: sync vs async, Jev vs local

    Setup. Entry 3's 12 React/SwiftUI tasks ran twice under four conditions, 96 runs in all:

    • no hook;
    • Jev, synchronous;
    • Jev in the background with asyncRewake: findings arrive as a system message when ready, and the agent never waits;
    • local Kev-4B in the background.

    Both rule packs were on, gated. Luna graded the final code and reviewed it blind.

    {{CHART_E5}}

    Right-hand group: minutes per task, doubled so it shares the scale.

    {{E5_TABLE}}
    • Every hook condition cut violations significantly, by about 1 per task out of 2.4. The 95% intervals exclude zero, and 13–15 of 24 tasks improved while 3–5 got worse.
    • Async is as effective as sync and costs less time. It added +10 s per task against +16 s. In headless runs the background findings still arrived: in the pilot, the agent added type guards right after an async "unvalidated JSON" finding.
    • One signal disagrees. The AI reviewer's comments that our rules cover fell with sync Jev (0.96 → 0.50 per task) but not with async (1.00). Those counts are small, about 24 comments per condition, so this needs a bigger run before it means anything.
    • Local Kev in the background worked, expensively.
      • It matched Jev on violations (1.25 per task).
      • It showed 71 double-check findings, many of them noise, which the agent spent edits on.
      • Its checks averaged 9.4 s with four agents sharing one server.
      • Net: +52 s and +60% cost per task. So it's usable as a background judge, but not better than Jev until it's more precise.

    Codex runs

    The broken Codex install turned out to be a stale npm shim; a working Homebrew Codex (0.157.1) was already installed. Codex supports synchronous hooks: apply_patch events are parsed from their + lines, and findings go back as context. It has no rewake, so the Codex runs are synchronous. Setup: the same 12 tasks, twice each, with the user's default Codex model (gpt-6-astra, medium) and an isolated Codex home per run.

    {{CODEX_TABLE}}

    The hook cut Codex's graded violations by 45% (1.67 → 0.92 per task), with an interval that excludes zero, for about 6 s more per task. In the smoke test, Codex had been told to cast the JSON; after the hook's finding, it replaced the cast with runtime validation.

    Fine-tuning plan

    • Jev's outputs can't be training data. TypeSafe's Master Customer Agreement prohibits using "the Services or any Output to perform model distillation, train a model to imitate the output of the Services, or develop… a similar or competing product". So the teacher can't be Jev.
    • What we can use: our labeled edits. That's about 950 cases, roughly 10,000 rule judgments, labeled by Claude subagents and not by Jev. Train only on the tuning split, and keep every held-out file untouched for evaluation. The model providers' terms on using generated data for training should be checked before any release.
    • Recipe: Kev's own fine-tuning path, starting from the released checkpoint (--init_from jaredpalmer/kev-4b). Kev-4B first, then Kev-0.8B. Its authors report about $1 per Kev-4B run on an H100, or it can run locally on MLX with one job at a time.
    • Bar to beat:
      • held-out F1 of at least 90%;
      • clean-edit false alarms of at most 5%;
      • a gated median of at most 1 s on this Mac (0.8B).
      Then re-run the Entry 5 E2E with the fine-tuned model in the background.

    Entry 4 · Local models on the Mac 26 Sep 2026

    Question. Can a Jev-like model running on this machine (M3 Max, 64 GB) replace the API call? The goal is zero cost per edit and lower latency, ideally using the Apple Neural Engine.

    Setup. Three open models all speak the same /v1/systemone protocol, so the hook and harness only needed a base-URL switch (TYPESAFE_BASE_URL):

    • Kev-0.8B and Kev-4B, fine-tuned Qwen models running on MLX (the GPU, bf16);
    • Laya, a 421M-parameter ModernBERT encoder, on PyTorch's Metal backend.

    The rules and held-out edits are the same as in Entries 1 and 3, with the same 0.8 / 0.5 thresholds. Requests ran one at a time so the timings aren't shared. No model was fine-tuned: this is zero-shot.

    Accuracy

    {{CHART_LOCAL_F1}}

    "Best threshold" is Kev-4B's F1 at whichever cut-off suits it best, which was 0.6 in every group. It's picked on the held-out data, so it flatters Kev-4B.

    Full table for all three local models{{LOCAL_TABLE}}
    • Kev-4B is the only usable one, and it's well behind. Its F1 is 54–67% with both tiers, and 61–74% at its best threshold, against Jev's 96–99%. Its high tier is precise ({{KEV4_HIGH}} findings real) but catches only 14–31% of violations. Its double-check tier flags 25–74% of clean edits.
    • Kev-0.8B and Laya are close to chance on code. Their F1 is 13–34%, and they flag most or all clean edits. On a two-rule probe, Kev-0.8B even scored the clean file higher on "empty catch" than the file that had one.
    • Laya's context limit is a structural problem. The English checkpoint reads 512 tokens, and larger edits are cut off.

    Speed

    {{CHART_LOCAL_LAT}}

    Every local model was slower than calling Jev's API. Kev-4B's 90th percentile reached 8–10 s on long Swift and practice-rule edits, and one request timed out. Running locally removes the per-call cost (about $1.51 per 10,000 edits with Jev), but it adds seconds to every agent edit.

    The Neural Engine

    Kev runs on MLX, which uses the GPU, not the Neural Engine. Laya is the natural candidate for it: an encoder with no text generation. We exported its encoder to ONNX and ran it through ONNX Runtime's Core ML provider. The export matched PyTorch to within 1e-4.

    {{BENCH_TABLE}}

    One lint request is 21 rules × 512 tokens. "Core ML coverage" is how much of the graph Core ML accepted; the rest ran on the CPU.

    • Core ML accepted only 144 of 1,677 graph nodes. ModernBERT's attention and masking ops fell back to the CPU in 29 separate pieces, so every compute-unit setting ran at CPU speed (15–22 s).
    • Converting the PyTorch model straight to Core ML with coremltools failed on unsupported ops (new_ones, then boolean mask arithmetic). Patching those is a project of its own.
    • Even a perfect port wouldn't beat Jev. Laya encodes the code once per rule, about 10,000 tokens for 21 rules. That's roughly 8.6 trillion operations, which takes at least half a second at the M3 Max Neural Engine's quoted 18 TOPS, and more in practice. Jev and Kev encode the code once for all rules.

    Can it be faster?

    We profiled Kev-4B on real held-out edits: a 6-line edit and a 138-line edit, a new edit versus the same edit sent again. Kev already runs on the GPU (Metal, through MLX). Cold start from launching the server to the first answer was 22.8 s, so it has to stay resident. All numbers below are warm.

    Rules asked6-line edit, new6-line edit, repeated138-line edit, new138-line edit, repeated
    10.56 s0.23 s2.52 s0.29 s
    51.46 s1.19 s3.61 s1.23 s
    13 (hygiene)3.98 s3.44 s3.59 s2.02 s
    23 (both packs)8.49 s7.90 s5.95 s5.10 s
    • The number of rules dominates. Each rule is a separate "row" that re-reads the cached code. On Metal, Kev runs those rows one at a time: its source says so, to keep memory bounded. That costs roughly 250–350 ms per rule even on a 6-line edit.
    • The code itself is cheap once cached. Re-sending the same 138-line edit with one rule dropped from 2.5 s to 0.29 s, thanks to Kev's prefix cache. Shortening the rule text by half (dropping the criteria) cut the 6-line case only to 6.1 s. It's the row count, not the words.
    • Levers, in order of payoff:
      1. Ask only rules that apply to the file. A cheap keyword gate (React rules only when hooks or JSX appear, SwiftUI rules only with import SwiftUI) would often cut 23 rows to 5–8. That helps Jev's cost too, but needs its own recall check.
      2. A smaller fine-tuned model. The 0.8B model's rows are several times cheaper, if fine-tuning brings its accuracy up.
      3. Batch rows on Metal. That's a change inside Kev's MLX path.
      4. An async hook, so the agent isn't waiting at all.
    • A faster GPU mostly means a different machine. Kev batches rows with CUDA graphs on NVIDIA, but a server on the DGX Spark adds a network hop and isn't "local" in the zero-cost-on-this-Mac sense.

    Estimate: with gating plus a fine-tuned small model, 0.5–1.5 s per edit on this Mac looks plausible. Beating Jev's ~0.3 s locally is unlikely without batched rows.

    What we learned

    1. Zero-shot local models can't judge these rules yet. Kev-4B is the closest, at about 70% F1, and it's 7–14× slower than Jev's API on this Mac.
    2. The Neural Engine isn't reachable with today's exports, and Laya's one-pass-per-rule design would cap its speed anyway.
    3. The promising path is fine-tuning, not a bigger download.
      • Kev ships a fine-tuning recipe, reported at about $1 per Kev-4B run.
      • Our labeled edits (roughly 9,000 rule judgments) are a ready training set.
      • Rules and cases can be generated further by the jev-lint-rules skill.
      • Training on Jev's own outputs would need a check of TypeSafe's terms first.
    4. Latency can be hidden instead of beaten. Claude Code hooks can run in the background and wake the agent only when a finding comes back (asyncRewake). A slower local model might then be fine, but this is untested.

    What we learned

    1. Wording is the whole game. Jev answers the words, not the intent. Rules need the exact pattern plus explicit exceptions ("WebSockets are not HTTP requests"). One tuning pass, checked on unseen edits, removed most false alarms.
    2. Jev catches patterns, not reasoning. It finds "cast JSON without validating" every time, but not "two polling loops can race".
    3. A hint beats a review comment, where the rules match the work. The agent fixed hook findings in its next edit. On React tasks, the reviewer had far fewer rule-covered issues to raise. The Swift practice rules rarely matched what the reviewer cared about (5 of 44 findings), so there was little to prevent.
    4. Luna is a strong alternative judge. It's slightly more accurate on these rules, but about 5× slower per edit, and it doesn't return probabilities for tiering. Jev's speed matters because the hook runs on every edit.

    Entry 1 · Hygiene pack 26 Sep 2026

    Question. Following the forwarded post: convert coding guidelines into tiny rules that are easy to judge, and run Jev on every edit in a PostToolUse hook. Findings come back in two tiers. Does it work in TypeScript and Swift?

    What we built. src/hook.ts works in Claude Code and Codex. It extracts only the code the edit added, including the + lines of a Codex patch. It asks one yes/no question per rule in a single Jev call, and returns findings as extra context. It never blocks, and if Jev is slow or down it stays silent. There are 13 rules per language, such as no any, no empty catch, no restating comments, and no magic numbers.

    Labeled edits

    {{N_H_ALL}} synthetic hook payloads, split into tuning and held-out sets. The original comparison used GPT-5.4-mini as the LLM judge (see Entry 2 for both baselines side by side).

    • Jev: 99% held-out F1 in both languages at p ≥ 0.5, and no false alarms on clean edits.
    • GPT-5.4-mini: 90–94% F1, and it flagged 8–21% of clean edits superseded baseline.
    • Regex: 61–66% F1 overall, because it can express only half the rules.
    • Run-to-run stability: Jev's probabilities moved by at most {{CONS_MAX}} across repeats (99th percentile {{CONS_P99}}).
    • Weak spots: rules that need counting (nesting depth: 70% recall) or tracing (floating promises: 75%).

    Real agent runs

    Claude Code (Sonnet) did 12 general tasks, such as a GitHub client, a rate limiter and a disk cache. Each ran twice under three conditions: no hook, both tiers, and high tier only. GPT-5.5 graded the final files blind.

    • The agent acted on the feedback. It fixed 19 of 20 high-tier findings, and mechanical violations went to near zero. For example, Swift force-unwraps fell from 6 to 1.
    • The overall effect was small. Violations per task went from 2.29 to 1.83 with both tiers, and to 1.71 with the high tier only. The 95% interval includes zero.
    • Why. The agent already wrote fairly clean code, and most of what remained were judgment calls on names and numbers.

    These numbers used the hygiene pack only. The full v1 page is kept at report/archive/2026-09-26-v1-hygiene-report.html.

    Jev vs the grader on real code

    On 98 real agent-written files, Jev and GPT-5.5 agreed on mechanical rules. They split on vague names and magic numbers. Mostly that was the grader reading the rule literally: let (data, _) = … fails because data is on the banned list, and defaulted option values count as magic numbers. Jev's one clear miss was four-level nesting.

    Recommendation

    1. Install the hook with both packs in Claude Code (and Codex once its CLI is fixed on this machine). Run it as a non-blocking hint with thresholds 0.8 / 0.5, and pin JEV_LINT_MODEL=jev-1.13.0.
    2. Match the setup to your review process. With human review or no per-change AI review, run the hook, async and always on. If an AI reviewer plus a fix round already run on every task, the hook is marginal (Entry 6). Consider a review-time Jev check instead, which is cheaper and untested.
    3. Keep the gate on (the default). It skips about two thirds of rule checks per edit at no measured recall cost.
    4. In Claude Code, run it async: asyncRewake: true with JEV_LINT_MODE=rewake. It's as effective as synchronous and saves about 6 s per task, though a larger run should confirm it before relying on it. In Codex, keep it synchronous, since Codex has no rewake.
    5. Let each repo learn from the hook. The findings log records what fired and whether the agent fixed or kept it. Run the jev-lint-learn skill weekly on active repos: it turns recurring fixes into AGENTS.md guidance, and repeatedly ignored flags into rule rewrites. In its first real use, it narrowed this repo's own stdout rule after a false positive.
    6. Keep the AI code reviewer. The hook handles the pattern-level issues cheaply before review, so review time goes to logic and design, which is where about 75% of review findings were.
    7. Treat rule wording like code. Before adding a rule, add labeled examples and hard negatives, tune on the dev split, and accept it only if the held-out split holds up. The harness does this in one command.
    8. Consider the high tier only for practice rules if noise shows up in practice. Their double-check band was 64% real, compared with 86% for hygiene rules.
    9. Move nesting depth and floating promises to ESLint/SwiftLint. Jev is weak at counting and tracing.

    Methods

    • Jev: jev-latest (jev-1.13.0), one call per edit, one yes/no question (a Noul) per rule. $0.042 per million input tokens; output tokens are free.
    • LLM judge, grader, reviewer and mapper: GPT-6-Luna at reasoning_effort: low. $0.10 per million input tokens and $0.50 per million output, standard tier, checked 26 Sep 2026. Entry 1 originally used GPT-5.4-mini and GPT-5.5.
    • Codex (Entry 5): codex-cli 0.157.1 (Homebrew), gpt-6-astra at medium reasoning (the user's default), codex exec with an isolated CODEX_HOME per run and --dangerously-bypass-hook-trust.
    • Local models (Entry 4): Kev-0.8B and Kev-4B (jaredpalmer/kev-*, MLX, bf16); Laya 0.3.20 English checkpoint (PyTorch Metal backend; ONNX Runtime 1.30 with the Core ML provider). Held-out split only, one request at a time, on an M3 Max with 64 GB.
    • Agent: Claude Code headless (Sonnet). User hooks, plugins and MCP servers were off. Hook conditions were interleaved.
    • Labels: written by Claude subagents, one labeler per edit. Tuning and held-out sets come from different authors. Thresholds were fixed at 0.8 / 0.5 before any data came in.
    • Caveats:
      • The labels are synthetic.
      • Luna is both the competitor and the grader, so shared blind spots could favour it.
      • The end-to-end samples are small: 24 runs per condition.
